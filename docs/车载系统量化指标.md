本文所有数字均为**在实机上测得**，并注明测量方法；优化项给出前后对照。

| 项目 | 数值 |
|------|------|

| 内存 | 497MB（MemTotal 508916kB） |
| 屏幕 | 800×480 RGB LCD，`/dev/fb0` 32bpp、stride 3200 |
| 根文件系统 | eMMC `mmcblk1p2`（ext3） |

| CPU 口径 | `/proc/<pid>/stat` 的 utime+stime 差值，HZ=100 → **jiffies/秒 ≈ 单核百分比** |

### 图标优化做了什么

首页 7 个入口图标原来是 **1254×1254 的 PNG（单张 1.1~1.4MB，合计 7.4MB）**，
实际显示尺寸只有 86×86。改为预缩放的 **172×172（≈25~35KB/张）** 后：

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 应用二进制 | 7.98MB | **0.55MB** | **-93%**（大图原样嵌在 Qt 资源里） |
| 启动到首页首帧 | 8161ms | **4979ms** | **-39%** |
| 首页常驻内存 VmRSS | 70184kB | **29028kB** | **-60%**（约 41MB，正好对应 6 张 1254²×4B 的位图缓存） |

## 四、摄像头链路（V4L2）

| 指标 | 实测值 | 方法 |
|------|--------|------|
| 应用请求 | 320×240 @15fps | 代码 `startCapture(dev, 320, 240, 15)` |
| 摄像头实际支持 | MJPG 1280×720@30 / 640×480@25；YUYV 1280×720@10 / **640×480@25** | `VIDIOC_ENUM_FMT` + `ENUM_FRAMESIZES`（自研 `scripts/v4l2_enum`） |
| **实际协商结果** | **640×480 YUYV** | 应用日志 `CAMERA ... size=640x480 fourcc=YUYV` |
| 驱动交付帧率 | **21.5~21.8 fps** | 统计 `VIDIOC_DQBUF` 成功次数 |
| 转换（YUYV→RGB）帧率 | **~11 fps** | 统计转换成功并 emit 次数（默认 80ms 节流） |
| 上屏帧率 | **8.6~9.7 fps** | 统计 `setPixmap` 次数（GUI 100ms 定时器） |
| 丢帧率 | **20~28%** | （交付−上屏）/交付 |
| 预览 CPU | **54~62%**（单核） | jiffies 差值 |

**关键发现**：代码注释写的是"用 320×240 降低 YUYV 转换和 GUI 缩放开销"，
但这颗摄像头**根本不支持 320×240**，驱动把请求调整为 640×480——
每帧要处理 30.7 万像素而不是 7.7 万，**像素量是预期的 4 倍**。
这既是预览 CPU 长期 55%+ 的直接原因，也解释了此前"按帧率节流无效"的对照实验
（节流版 68~71 vs 关闭节流 70~71 jiffies/秒）：大头不在转换次数，而在每帧像素量。

## 五、性能归因实验（4 个"想当然"被逐个证伪）

首页构造里有一段稳定复现的 ~2.5s 开销，逐项排除结果：

| 假设 | 实验方法 | 结果 | 结论 |
|------|----------|------|------|
| 20MB 中文字体加载慢 | 临时把 `NotoSansCJK-Regular.ttc` 移出字体目录再启动（测完立即还原） | 只快 **135ms**（4684→4549ms） | **证伪**；且会丢中文，字体不能动 |
| PNG 解码/图片插件慢 | 探针分别用"资源 PNG 图标"与"样式矢量标准图标"创建首个按钮 | 2530ms vs 2503ms | **证伪**，与图片来源无关 |
| 图标主题查找（`standardIcon`→`QIcon::fromTheme`） | 首个按钮改用文件图标，不触发主题查找 | 2530ms | **证伪** |
| 首次 QSS 规则生成（polish） | 先创建一个带样式表的 QLabel，再创建按钮 | QLabel 仅 211ms，按钮仍 2.5s | **证伪** |
| 控件类型（QToolButton 特有） | 首个按钮分别用 QPushButton / QToolButton | 2470ms vs 2503ms | **证伪** |
| **首次创建"带图标的按钮"本身** | 以上实验合并 | 第一个按钮 2.47~2.53s，**其后每个按钮 7~25ms** | **成立**：Qt 5.12.9 在本板的一次性开销 |

这条结论的价值不在"省了时间"，而在于给出了**不能再优化的边界**：
启动下限 ≈ QApplication 初始化 1.44s + 首次按钮 2.5s ≈ 3.9s，当前 4.98s 已接近该 Qt 构建的下限。

## 六、传感器与推流

### 板载传感器/驱动的实测能力（应用层直接依赖）

应用侧只调 open/read/write/ioctl 与 input 子系统，能力上限由驱动决定，
下面每个数字都在板上量过（`scripts/drv_rate`、`scripts/sensor_lat`、设备树与源码）。

| 驱动 | 总线 / 机制 | 实测能力 |
|------|-------------|----------|
| GT9147 触摸 | I2C 100kHz + 下降沿中断 | **5 点触控**，800×480 坐标映射；空闲中断 0 次/秒，滑动按中断实时上报 |
| ICM20608 六轴 | SPI 8MHz | **读取 9280 次/秒**（0.1ms/次，3.000s 成功 27841 次、0 失败）；输出三轴加速度+角速度+温度共 7 通道 |
| DHT11 温湿度 | 单总线（GPIO 位操作） | **1 次/秒**（协议下限 ≥1s，实测 0.9~1.1 次/秒）；单次读取阻塞 29.3ms |
| SR04 超声测距 | GPIO 触发/回响 | **最高 20 次/秒**（实测 49.7ms/次，3.034s 成功 61 次） |
| SR501 人体检测 | GPIO 双边沿中断 + 等待队列 | **事件驱动**：`read()` 阻塞等待状态变化（`wait_event_interruptible`），不适用轮询速率指标；触发到应用响应 32~101ms |
| AP3216C 光照/距离 | I2C 100kHz | 光照 / 距离 / 红外三通道读取（ioctl） |
| 蜂鸣器 | GPIO（gpio5_1） | 开关控制（write） |
| 背光按键 | GPIO 中断 | input 子系统按键事件（`KEY_BACK`） |

> 口径提醒：ICM20608 的 9280 次/秒是"**单次 read 取一帧完整采样**"的速率上限，
> 不含应用侧解析与界面刷新；SR501 用 `drv_rate` 测会一直阻塞，这是它事件驱动的
> 正常表现，不是故障。

### DHT11（首页温湿度）

| 指标 | 实测值 | 方法 |
|------|--------|------|
| 单次读取阻塞 | **平均 29.3ms，最大 30.9ms** | 自研 `scripts/sensor_lat`，4 次、间隔 1.2s |
| 调用位置 | **GUI 线程**（`HomePage::updateEnvironment`） | 代码审查 |
| 驱动内部保护 | `msleep(18)` + 1s 最小间隔（`drivers/smarthome/dht11.c`） | 源码 |

风险：单次 29ms 的界面线程阻塞已能感知；若驱动 1s 间隔保护被触发
（例如板载设备页采集线程刚读过），**最坏可在 GUI 线程阻塞 1s**。

### MJPG-streamer 远程视频（哨兵监控）

| 指标 | 实测值 | 方法 |
|------|--------|------|
| 参数 | 640×480 @25fps，`-q 70` | 与应用相同命令行 |
| 码率 | **22.5 Mbps**（33.67MB / 11.999s） | 主机 `curl` 拉 `http://192.168.31.50:8080/?action=stream` |
| 帧率 | **25.0 fps**（300 帧 / 12s） | 统计 JPEG SOI 数量 |
| 平均帧大小 | 112KB | 字节数 / 帧数 |

## 七、按简历 5 条的量化文案（数字已填）

1. **Qt 界面与页面管理**：800×480 LinuxFB 触摸界面，**7 个功能页（页面层 3224 行 + 服务层 2381 行）**、
   `connect()` **116 处**；进程启动到首页首帧 **8.16s → 4.98s（-39%）**，
   首页常驻内存 **70MB → 28MB（-60%）**，应用体积 **7.98MB → 0.55MB（-93%）**；
   页面二次切换仅 3~16ms（懒构造）。
2. **V4L2 采集链路**：完成 **9 个 ioctl** 完整采集流程；用 `ENUM_FMT/ENUM_FRAMESIZES`
   定位到"请求 320×240 但硬件不支持、实际协商 640×480"的问题；实测驱动交付
   **21.7fps**、转换 **~11fps**、上屏 **8.6~9.7fps**、丢帧 **20~28%**。
3. **多线程与渲染策略**：采集线程只更新最新帧缓存，GUI 以 100ms 定时器取帧；
   用对照实验推翻原先的优化假设（节流版 68~71 vs 关闭节流 70~71 jiffies/秒），
   把 CPU 主因重新定位为"每帧像素量是被请求值的 4 倍"；预览 54~62%、板载设备页 11~17%、首页空闲 0.5~4%。
4. **哨兵监控**：SR501 300ms 轮询、无人 10s 自动停流；MJPG 推流实测
   **25fps / 22.5Mbps**，推流进程仅占 **5%** 单核。
5. **分层与解耦**：6 个服务模块覆盖 8 个设备接口；量化出**页面层唯一一次业务级设备访问**
   （首页直读 /dev/dht11，单次阻塞 29.3ms）；用 4 组对照实验把 2.5s 启动开销定位到
   "首次创建带图标按钮"这一 Qt 一次性行为。
